### #1 note 収益化は「ジャンル選定」が命

- **URL**: https://note.com/dandy_moose6452/n/n1eed79235a9c
- **著者**: Yuga-湧雅- (セミリタイア中の 40 代・2 児の父)

**要約**: noteで有料記事を売るには「ジャンル一本化」が最重要。複数ジャンルアカウントは読者が定着せず売上が安定しない。著者はニッチで失敗 → アカウント消去 → レッドオーシャン (副業・美容・恋愛など見込み客がいるジャンル) で勝負して 3 日で初売上達成。「狭く深く」が収益化の最短ルート。

**主要な学び**:
1. ジャンル統一の必要性 — 複数ジャンルは「何の人か分からないアカウント」になり、お金を払う動機が生まれない
2. 読者心理 — 人は「専門家 (プロ)」から情報を購入する
3. レッドオーシャン戦略 — ニッチより、見込み客がいるジャンルの方が成功しやすい
4. 戦略性の不可欠さ — 「なんとなく」では売れない

**刺さる引用フレーズ**:
- 「**何の人か分からないアカウントからわざわざお金を払う人はいない**」
- 「**狭く、深くが絶対の正義**」
- 「**有料にすれば誰か買ってくれるだろうという人は来世でも売れない**」

**gaku_ai_life への反映**:
- 既に「駆け出しSE × AI × note 副業」とジャンル絞り済み = この方針は正しい
- ただし「298k バズで時事ネタ枠 1/10」(D-031) は本記事の警告「複数ジャンル = 売れない」と緊張関係
- **示唆**: 時事ネタ枠は手動・告知性に絞り、本軸の「狭く深く」は守り続ける現方針が正解

### #2 自分の強みは、すぐ隣にあるから気付いてあげて

- **URL**: https://note.com/ryoutamori866/n/nfdb02fa7383c
- **著者**: もりりん (note 副業で稼ぐ残業エンジニア)

**要約**: 副業で結果を出す人と自分を比較して自己否定に陥る人が多い。しかし自分の強みは身近な「当たり前」の中に隠れている。一人で悩まず家族・友人に「私のいいところは？」と聞くことが発掘のカギ。

**主要な学び**:
1. 強みは「当たり前」に隠れている — 自分にとって常識的なことが、他者には差別化要因
2. 比較による自己否定の危険性 — SNS で同期の成功を見ると陥る陥穽
3. 他者フィードバックの重要性 — 自分では気づけない強みを発見する具体策

**刺さる引用フレーズ**:
- 「**自分にとっては当たり前だけど 他人には羨ましく見える**」
- 「**自分の『当たり前』の中にこそ、最強の武器が眠っている**」

**gaku_ai_life への反映**:
- gaku_ai_life の差別化軸の再点検: 「コード触ったことない会社員向けに AI を教える」は SE のオーナーには「当たり前」だが、ターゲット層には特別な価値
- **新規 Threads 投稿型の追加**: 「ぼくが当たり前にやってる○○、コード触ったことない人にはこう見える」
  - 型 D (強み転換型): `[自分が当たり前にやってること] って、コード触ったことない人にはこう見えるんですね`

### #3 「絶対読まれない文章」を作ってしまう人が多すぎる ★★★

- **URL**: https://note.com/watanabesanb/n/n8e4621239905
- **著者**: ワタナベシンスケ (ブランディング実績 12,000 件以上)
- **公開**: 2026-05-20

**要約**: Web 媒体と紙媒体の根本的違いを理解せず、雑誌調の丁寧で正確な文体を SNS に持ち込むと読まれない。重要なのは「結論先行 (PREP 法)」と「最初の 13 文字でキャッチを決める」こと。正確性より「つかみ」の上手さが認知拡大と集客につながる。

**主要な学び**:
1. 紙媒体 vs Web 媒体の本質的違い — 紙=目的読者 / Web=通りすがり
2. PREP 法の活用 — Point→Reason→Example→Point で結論先行
3. **最初の 13 文字の重要性** — タイトルやファーストビューで視線を留める
4. 「正確さ」より「つかみ」 — 丁寧説明より煽り気味の問いかけが反応を生む
5. 認知拡大が売上の前提条件 — 8〜9 割の「見てるだけ」層へのリーチが集客に

**刺さる引用フレーズ**:
- 「**丁寧な説明や正確な説明が、あなたを押し上げるのではありません**」
- 「**知ってもらわなければ、最終的なお客様にもなりようがありません**」
- 「**その向こう側に 8 割〜9 割の見てるだけの人がいます**」

**gaku_ai_life への反映 (最重要・即適用)**:
- **D-031「バズ型 5 要素」と完全一致**: 「冒頭固有名詞 + 60-80字短文 + 強い断定 or 逆説問いかけ」= 13 文字キャッチの実装
- **既存 note 記事のタイトルを 13 字以内に再点検**:
  - `想定外の 298,189 views` ← 14 字。OK
  - `298k views の裏中` ← 11 字。最適
  - 連載 Part1 各章タイトルも 13 字以内推奨
- **Threads 投稿冒頭も 13 字フック**:
  - 例: 「173 本書いて気づいた」「298k 出た日のこと」「Claude Pro やめた話」
- **feedback/gaku_ai_life.md に「13 字キャッチ」ルール追記検討**

### #4 SKILL.md を使ってる人は全員 "gh skill" も知っておいてください

- **URL**: https://qiita.com/TooMe/items/c9e42de497a9eff2b680
- **著者**: @TooMe (KDDIアジャイル開発センター)

**要約**: GitHub CLI v2.90.0 で追加された `gh skill` コマンドの解説。SKILL.md (Agent Skills) の検索・プレビュー・インストール・更新・公開を 1 コマンドで完結。Claude Code / GitHub Copilot / Cursor など 30+ AI エージェント対応。

**主要な学び**:
1. `gh skill` は Skill の npm install — 外部 Skill 取り込みが対話式
2. 複数エージェント同時インストール対応 — チーム全体の指示書を一度に統一
3. セキュリティ最優先 — `preview` 確認と `--pin` バージョン固定が必須
4. スコープ分離 — `project` (チーム共有) と `user` (個人環境) の使い分け
5. Preview 版制限 — 削除サブコマンド未実装、検索精度に課題あり

**Threads ネタ案**:
- 「**意外と知らない、`gh skill` で○○が変わった**」(気づき型)
- 「**Before: 手動 copy / After: 1 コマンド**」(対比型)
- 「**インストールは自己責任。GitHub による検証はない**」(警告型)

- **著者**: shuntaka (takahashi-shunichi)
- **公開**: 2026-05-01

**主要な学び**:
1. キーバインド最適化 — Option キー統一で視線移動と同速操作

### #6 品質の言語化のススメ — 早期テストの原則を Claude Code Agent Skills で実現

- **URL**: https://tech.layerx.co.jp/entry/articulatin_quality
- **著者**: 小山 (LayerX QA エンジニア)

**要約**: 品質基準やテスト戦略を明確に言語化することで、Claude Code が AI Agent Skills として自動リスク評価し、適切なエラーハンドリング・テストを生成。テストカバレッジが **65% → 95%** に向上した実践記録。

**主要な学び**:
1. 言語化の重要性シフト — 人間の役割は「あるべき姿を定義 (言語化) すること」へ転換
2. JSTQB 原則の活用 — 「早期テストで時間とコストを節約」を AI 時代に適用
3. 多層的な定義 — 目指す品質 / リスク基準 / テストスコープの 3 層
4. 測定と改善のサイクル — Evals で定量検証 (95% カバレッジ達成)
5. HITL (人間ループ) — AI が不明な場合は人間に質問するフィードバック設計

**刺さる引用フレーズ**:
- 「**AI がコードを書く時代において、人間の重要な役割は『あるべき姿を定義すること』へとシフト**」
- 「**今目指すべき品質のゴールは何か。今守るべきリスクは何か。**」

**Threads ネタ案**:
- 「**テストカバレッジ 65% → 95%。変わったのは？品質基準の『言語化』**」(対比型)
- 「**AI 時代、エンジニアの仕事は「書く」から「定義する」へ**」(時代観型)

### #7 Zenn でも Note でもない、自分が欲しかった記事投稿プラットフォームを作った

- **URL**: https://zenn.dev/devken/articles/kakubase-why-i-built-it
- **著者**: devken (フロントエンドエンジニア)

**要約**: 既存プラットフォームの課題を解決するため、Zenn の GitHub push 連携と Note のリッチエディタを組み合わせた記事投稿プラットフォーム「kakubase」を開発。AI 時代のローカル執筆ワークフローを実現。

**主要な学び**:
1. プラットフォーム選択の課題認識 — 各サービスの長所と短所を言語化
2. GitHub 連携の重要性 — 「AI が自分で書いた記事を読んで、自分で Skill を作って、自分で実行」
3. UX バランス — リッチエディタを「ちょうどいい」水準に調整するのが最大の課題
4. データ所有権の誠実性 — GitHub に原本保持でサービス終了リスク対策
5. 実行力による差別化 — 構想 → サービス化 → npm ライブラリ提供まで完遂

**刺さる引用フレーズ**:
- 「**エンジニアにとって自然なワークフローそのままで記事が投稿できる気持ちよさは唯一無二**」
- 「**AI 時代においてローカルで書いて push するワークフローはますます重要に**」
- 「**GitHub に原本が残る設計**」 (信頼性)

**Threads ネタ案**:
- 「**Zenn でも Note でもない、ぼくが欲しかったやつ**」(共感型)
- 「**個人開発で「ないなら作る」までできる時代**」(時代観型)
