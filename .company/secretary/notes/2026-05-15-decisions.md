## D-015: 投稿の同質性回避 (冒頭バリエーション 8 種類 + プロンプト強化)

### 何を解決するか
オーナーの相談「AI で生成される投稿文が似たようなものばかり」。
診断結果:
- queued 10 本 + posted 6 本の冒頭を分析 → **3 パターンに 7 割集中**:
  - 数字 + 主語 + 動詞 (6 本): 「フォロワー134、〜」「土日2日で〜」「朝の通勤30分、〜」「3週間で〜」
  - 主語省略 + 名詞 (3 本): 「副業が続かない理由、」
  - 質問型 (3 本): 「投稿しんどい時ありますか？」
- テーマも「AI × 副業 × SE」の三角形に 8/10 本集中
- 根本原因: `feedback/<account>.md` の「良かった例」が **「再利用パターン」として明示登録**されていて、AI が機械的に模倣

### 設計

**A. feedback ファイルに「冒頭バリエーション集 A〜H」追加**

8 種類のパターン + 各 4 つの例:
- A: 数字先行型 (Day1初投稿型・連発禁止対象)
- B: シーン先行型 (場面・情景から)
- C: 失敗オープン型 (弱さから)
- D: 質問・問いかけ型
- E: 対比・逆張り型
- F: 引用・他者の声型
- G: 未完型 (続きを匂わせる)
- H: 動作・観察型 (淡々と)

明示ルール:
- 直近 5 本で使った型は禁止
- 10 本生成時に最低 5 種類使う
- ★★★★★ 手本パターンは 10 本中 1 本まで

**B. `generate_posts_via_claude` プロンプト強化**

新規ルール 7 項目を追加:
1. 直近 14 日の posted を全部読む
2. 冒頭 1 行の同パターンを連発しない
3. A〜H から最低 5 種類使い分け
4. ★パターンは 10 本中 1 本まで
5. 数字の単位多様化 (時間/金額/人数/回数/期間/距離/容量)
6. テーマ分散 (AI/副業/SE 以外を 10 本中 3 本)
7. frontmatter に `hook_pattern: A` (使った型) を記録

### 選択肢の検討
| 案 | 内容 | 採用判断 |
|----|------|---------|
| A | プロンプトだけ強化 | △ feedback 側のテンプレが残ったまま、再発する |
| B | feedback に「禁則リスト」だけ追加 | △ AI が代替パターンを思いつかない |
| **C** | **feedback にバリエーション集 (A〜H) + プロンプト強化の併用 (採用)** | ✅ 「禁止」と「代替」の両方を提示 |
| D | A/B テスト機能を先に作る | △ 時間かかる・効果検証は後でも可 |

### Why
- 半自動化のジレンマ: 「良かった例を残す → AI が学ぶ → 同じ再生産」を構造的に解消
- 「直近の冒頭を読んで避ける」+「代替の型を 8 種類提示」のセットで根本対策
- frontmatter `hook_pattern` 記録により、後から「型別の数字勝負」(A/B テストの土台) が可能に
- 商品配布物としても訴求点になる: 「**画一化を機械的に防ぐ仕組み**を内蔵」

### 検証方法
次回 `/post_bulk count:10` の出力で:
1. 冒頭パターンが 5 種類以上に分散しているか
2. テーマが AI 以外を 3 本含むか
3. 「フォロワー134、〜」を 1 本だけに収まっているか
4. 各下書きの frontmatter に `hook_pattern` が記録されているか

### 残課題 (Phase 2)
- `nightly_pipeline.py` 経由の `/threads-daily-run` でも同ルール適用 (今は /post_bulk のみ)
- 投稿の **メトリクス × hook_pattern** の相関分析 (どの型が一番伸びるか)
- A/B テスト機能 (D-016 候補)

## D-016: リサーチ結果の参照漏れ修正 (research/topics/ 直下も投稿生成で読む)

### 何を解決するか
オーナーの鋭い疑問「リサーチした情報も投稿のネタになっているか？」で**実装の穴が発覚**:

- `.company/research/topics/` 直下に大きなリサーチ結果が蓄積されていた:
  - `2026-05-14-collect.md` (8.5 KB) — Web リサーチ
  - `youtube-2026-05-14.md` (**1.2 MB**) — YouTube 字幕 + 抽出ネタ
  - `post-pattern-2026-05.md` (7 KB) — 自己分析
- でも `/post_bulk` のプロンプトは **`inbox/` しか読んでなかった**
- → せっかく `/research_youtube` で 1.2 MB の動画ネタを集めても、投稿生成では**完全スルー**

これは「リサーチ機能を作ったのに、生成側で活用されない」典型的な統合不足。

### 設計 (4 ファイル修正)

1. **`scripts/discord_bot.py` の `generate_posts_via_claude` プロンプト**
   - `A. inbox / B. 直下リサーチ / C. 競合手本` の 3 ソースを明示
   - `youtube-*.md` は大きいので「**末尾の要約セクションだけ Read**」を指示
   - {count} 本中、リサーチ結果反映を最低 {min(count, 2)} 本要求

2. **`.claude/skills/note-article-generate/SKILL.md`**
   - 入力データに `research/topics/` 直下の最新ファイルを追加
   - note 記事に「Web トレンド・YouTube 知見」を反映可能に

3. **`.claude/skills/threads-daily-run/SKILL.md`**
   - 既存の `post-pattern` `*-collect` に加えて `youtube-*.md` と `inbox/*.md` を明示追加
   - nightly_pipeline 経由でも参照されるように

4. **`.claude/skills/threads-create-post/SKILL.md`**
   - 「`research/topics/` の関連調査ファイル」だった曖昧記述を具体化
   - inbox / collect / youtube / post-pattern を明示
   - `/create_post` `/create_post_from_idea` でも参照される

### Why
- リサーチ機能を作っても、生成側で使われないと**投資ゼロ**
- 「機能を作る」と「機能を統合する」は別の工程。今回後者が抜けていた
- 商品配布物 (BLUEPRINT.md) としても重要: 「リサーチ → 自動的に生成に反映」がループとして成立してこそ価値がある

### 検証
次回の `/post_bulk count:10` で:
- 生成された下書きの中に Web トレンド由来の投稿が含まれるか
- youtube リサーチ素材から抽出されたネタが投稿に出るか
- frontmatter の `used_idea_ids` に inbox 以外の source も記載されるか

## D-017: Discord `/ask` コマンド (スマホから Claude に直接指示)

### 何を解決するか
オーナーの本質的な要望:
> 「君に直接指示をしていけば、より精度の高いものにできるので、Discord から指示をできるようにしたい」

これまで:
- `/post_bulk` `/research_*` などはスキル発動 (定型タスク)
- 自由な指示 (コード変更 / 設計判断 / 分析) は **PC のターミナルでしかできなかった**
- 結果、オーナーが外出中・布団・電車で「気づき」を実装に変えられない

### 設計

**`/ask <message> [save:True]`**:
- 内部で `claude -p "<システムプロンプト + 指示>" --permission-mode bypassPermissions`
- 別の Claude Code セッションがヘッドレスで起動
- 同じプロジェクト (`.company/`, `scripts/`, `BLUEPRINT.md`) を操作する権限を持つ
- Edit / Write / Bash / WebFetch すべて自動承認
- やり取りを `.company/secretary/inbox/<ts>_ask_<slug>.md` に永続化
- 過去の `/ask` 履歴は次回の `/ask` で参照される (文脈の連続性)

**システムプロンプトの設計** (「いつもの私」を再現する核):
- 必読: BLUEPRINT.md / CLAUDE.md / feedback / 最新意思決定ログ / 過去 ask 履歴
- 振る舞い: 指示の意図を汲む / Edit で直接変更する / 報告は箇条書き / D-XXX で記録
- 不明点は「❓確認が必要」と明示 (推測実行しない)
- 応答末尾に「✅ 完了」「❓ 確認が必要」「❌ 失敗」を必ず明示

### 重要な技術的制約 (オーナーへ正直に伝えた)
**「ターミナルで動いている "この" Claude セッション」に直接届ける手段は無い** (Claude Code の対話セッションは外部から差し込めない).
代替として **別の Claude (ヘッドレス) を起動** し、同じプロジェクトを操作させる.
ファイル経由で結果が見えるので、実質「Claude にいつでも指示」と同等の体験.

### 選択肢の検討
| 案 | 内容 | 採用判断 |
|----|------|---------|
| A | DM 経由で指示メッセージをファイル化、後で手動チェック | ❌ 即時性なし |
| **B** | **`/ask` で別 Claude をヘッドレス起動 (採用)** | ✅ 即時応答・ファイル変更・履歴永続化 |
| C | MCP サーバー化 | ❌ 設計重い・MVP の範囲外 |
| D | Anthropic SDK を Bot に直接組み込む | △ Claude Code の機能 (スキル / ツール) が使えない |

### Why
- オーナーが「思いついた瞬間に Claude に指示」できる = 半自動化の最終ピース
- スマホ完結率がほぼ 100% に
- 過去のやり取り (inbox) が学習素材として蓄積される好循環
- 商品配布物としても訴求点になる: 「**スマホで Claude に直接指示できる**」

### 制約・注意点
- 1 回の `/ask` で 1〜10 分かかる (claude headless の起動コスト)
- 別 Claude は「現セッションの私」が持つコンテキスト (今日の会話) を見れない → BLUEPRINT.md と意思決定ログから状況を読み取る
- 同時実行制限: 並行で `/ask` を投げると API レート制限の可能性 (要観察)

## D-019: 無料 note 記事の字数方針 (2000 字以内・スマホ前提)

### 何を解決するか
オーナー方針:
> 「無料記事が長いよね。2000 文字以内でいいと思う。みんなケータイで見るし、長いのは有料記事だけでいい。」

D-018 で生成された Day 3 記事は約 4500 字。**スマホで読むには長すぎ**。
無料 note は連載の入口（信頼導線）として「読み切りやすさ」が最優先。
深掘り・物語性で稼ぐのは有料記事だけに集約する戦略。

### 設計

**1. 既存 5/15 記事の短縮**
- `.company/products/articles/2026-05-15_day3-monoculture-fix.md` を 4500 → **1800 字** に圧縮
- 学び 5 → 学び 3
- セクション 8 → 5 (1 つの事件に絞る)
- メタオチ「これも AI が書いた」は残す (公開版 v3 と同じ余韻)

**2. `note-article-generate` スキル定義の改修**
- 「ゴール」セクションに「字数の方針」を新規追加
- `price: 無料` (デフォルト) → 1500〜2000 字
- `price: 有料` → 3000〜5000 字
- frontmatter テンプレートのデフォルトを `word_count_target: 1800` に変更

**3. 無料記事の構成テンプレート (1800 字以内)**
1. フック (100〜200 字)
2. 核心の物語 (500〜700 字・1 事件に絞る)
3. 学び 3 つ (300〜400 字)
4. ステータス + 余韻 (200〜300 字)
5. メタオチ or マガジン誘導 (100〜200 字・任意)

### 選択肢の検討
| 案 | 内容 | 採用判断 |
|----|------|---------|
| A | 既存記事は長いまま残す + 次回から短く | ❌ 公開する記事はすぐ短くしたい |
| **B** | **既存記事を短縮 + スキル定義も改修 (採用)** | ✅ 即効性 + 構造的な再発防止 |
| C | スキル定義だけ改修して既存はそのまま | ❌ 公開する前提なら短くすべき |

### Why
- スマホでの読み切り率が note の伸びを決める (滞在時間 > 字数)
- 無料は「Day X の核心 1 つ」だけに絞り、続きが見たい余韻で締める
- 有料は「字数 × 深掘り × 物語性」で勝負する役割分担を明確化
- BLUEPRINT.md の配布商品としても価値が出る:「**無料/有料の字数戦略を内蔵**」

### 圧縮の指針 (次回以降の参考)
- 「学び」は 3 つに絞る (5 つは無料には多すぎ)
- 横展開セクション (本筋以外) を統合 or 削除
- 詳細なコード例 / コマンド名は 1〜2 個に厳選
- 読者目線で「最初の 200 字で読み続けるか決まる」を意識
- 余韻のメタオチは 100〜200 字で完結させる
