# Day 2、朝起きたら自動化が止まってた話

## はじめに

「AI に Threads 運用を任せて、自分は意思決定だけする」を目指す note 実験記、Day 2 の記録です。

結論から言うと、**朝起きたら自動投稿が動いてませんでした。**

Day 1 で「全自動パイプライン完成、明日から AI が走り出す」と寝た 8 時間後に、起き抜けでこれです。正直、心が折れかけました。

ただ、ここから 1 日かけてリカバリした結果、**システムは Day 1 時点よりも明らかに堅牢になり、半自動化が一段階進化しました。**

その過程をすべて書き残します。同じような自動化を組もうとしてる人にとって、つまずきパターンとリカバリパターンの両方が参考になるはずです。

---

## 1. 朝、自動投稿が動いてなかった

5/14 朝、Threads アプリを開いたら、**7:30 に投稿されてるはずの朝の1本がない。**

最初、「あれ？昨日の queue 設定ミスしたかな」と思いました。電源は繋いだまま寝たので、PC が落ちてるはずもない。

`scripts/logs/threads_auto_post.log` を見ます。

```
===== 2026-05-14 07:44:07 START =====
[auto_post] 対象: 2026-05-13_99_discord-test-draft.md
[auto_post] 失敗: NameResolutionError: Failed to resolve 'graph.threads.net'
[discord] 通知失敗: NameResolutionError: Failed to resolve 'discord.com'
===== 2026-05-14 08:19:52 END exit=1 =====
```

**起動時刻が 7:44**（本来 7:30 のはず・14 分遅延）  
**DNS が引けず投稿失敗**  
**Discord 通知も同じ DNS エラーで失敗**  
**35 分間ハングしてからエラー終了**

3 つの異常が同時に起きてました。

## 2. 「電源繋いでたのに、なんで？」の落とし穴

最初に疑ったのは「PC がスリープした」でした。Windows の電源プランを確認します。

```
AC 電源時 standby-timeout = 0  (= スリープしない設定)
AC 電源時 hibernate-timeout = 0 (= 休止しない設定)
```

設定上はスリープしないはずです。タスクスケジューラの設定も `WakeToRun = True`（スリープしてても起こす）になってます。

**それなのに止まった。**

ここで結論を急ぐと「謎のスリープ」になるところでしたが、ログをもう一度読み返して気づきました。

- 起動は 14 分遅れて 07:44 にできた → タスクスケジューラは動いた
- が、DNS が引けない → ネットがつながってない
- 35 分間ハング → Wi-Fi 復帰待ちで止まってた

つまり**「PC は寝てた、けどスリープじゃない」**という、矛盾するような状態が真相でした。

## 3. 真犯人: Modern Standby

Windows 11 には **Modern Standby (S0 低電力アイドル)** という仕組みがあります。
これは「画面は消えてるけど CPU はちょっとだけ動いてる」状態で、メールやアラームは受け取れるが、Wi-Fi は省電力で頻繁に切れる。

`standby-timeout=0` は「**従来の意味のスリープ (S3) に入らない**」設定です。Modern Standby (S0) には適用されません。

タスクスケジューラは Modern Standby から PC を起こせる。しかし、**Wi-Fi が再接続するまでに数十秒〜数分かかる**。その間に Threads API を叩こうとして DNS で落ちる、というのが今回の事故の正体でした。

これは「電源繋いでてもスリープを防げてない」という、Windows 11 ユーザーが踏みやすい罠です。

## 4. 恒久対策：DNS リトライを全スクリプトに

対策は 2 段構えにしました。

**短期対策**: Python 側で DNS が引けるまで最大 3 分待つヘルパーを全自動化スクリプトに注入。

```python
# scripts/_net_wait.py
def wait_for_network(host="graph.threads.net", max_wait=180):
    deadline = time.monotonic() + max_wait
    while time.monotonic() < deadline:
        try:
            socket.gethostbyname(host)
            return True
        except OSError:
            time.sleep(3)
    return False
```

これを `threads_auto_post.py`、`threads_fetch_metrics.py`、`nightly_pipeline.py` の冒頭で呼ぶようにしました。**スリープ復帰直後でも DNS が引けるまで待ってから本処理に入る** ので、35 分ハングが再発しません。

**長期対策**: Modern Standby そのものを無効化する PowerShell スクリプト（`scripts/fix_modern_standby.ps1`）を作成。レジストリで `PlatformAoAcOverride = 0` を入れて、Wi-Fi アダプタの省電力設定もオフにします。管理者権限が必要ですが、1回実行すれば永続的に解決します。

## 5. ついでに発覚：Discord Bot が登録すらされてなかった

ここで秘書（Claude Code）が気づきました。

**「ところでオーナー、Discord Bot のタスクスケジューラ登録、確認してませんよね？」**

確認したら、案の定**未登録・未起動**。スクリプトは書いてあったのに、永続化されていませんでした。

「Day 1 で全部できた気になってたけど、最後の 1 ピースが抜けてた」のパターンです。

ここで `register_bot_task.ps1` を管理者 PowerShell で実行する流れに入ったんですが、UAC ダイアログを承認したのに `register_bot_task.ps1` 側で何かが詰まって、Bot タスクの登録に失敗しました。

詳細追跡は後回しにして、**暫定で `nohup python scripts/discord_bot.py &` で起動**。これで Discord は今すぐ動く状態に。永続化は次の運用日に再挑戦することにしました。

## 6. 教訓: 自動化は「壊れる前提」で組む

ここで強く感じたのは、**自動化は壊れる前提で組まないとダメ**ということです。

具体的には:
- **ログを必ず別ファイルに残す**: 35 分ハングの原因が追えたのはログがあったから
- **「成功」「失敗」のどちらでも通知する**: 沈黙＝正常の運用は危険
- **暫定起動の手段を常に持っておく**: タスクスケジューラが詰まっても手動起動できる
- **再起動なしで動くものから動かす**: 完璧を待つと運用が止まる

## 7. 「投稿を複数本ガンガン作りたい」→ /post_bulk 実装

午後、オーナーから要望が入りました。

> 投稿文をバンバン作成したい。Discord からの指示で投稿文を複数作成できるようにしてほしい。ガンガンフィードバックを入れるから。

これは半自動化の本質を突いた要望です。**ガンガン生成 → ガンガンフィードバック → ガンガン精度向上**のループ。

既存の Bot には `/generate_ideas`（ネタを N 本生成）はありましたが、**下書き本体を N 本生成**するコマンドはなかったので、新規追加しました。

```
/post_bulk count:5 theme:AI開発
```

これで `gaku_ai_life` の下書きを 5 本まとめて生成します。フィードバック蓄積（`.company/marketing/feedback/gaku_ai_life.md`）を**毎回必ず読み込んでから**生成するので、書き足すほど精度が上がります。

`/help` ガイドも 3 箇所更新しました。新コマンドを足したらヘルプも更新するのは基本だと、オーナーに指摘されて気づきました。

## 8. 基本設計書 BLUEPRINT.md を作成

午後の途中で「これ、配布商品として note で売れるのでは」という話になりました。

そこで `BLUEPRINT.md` を新規作成。**Claude Code に読ませると、購入者が自分の環境で同じ自動化を再現できる**設計書として。

13 章構成で、以下を網羅:
- システム全体アーキテクチャ
- ディレクトリ構造
- 必要な API キー一覧
- 各ファイルの役割
- セットアップ手順 9 ステップ
- カスタマイズポイント
- フィードバックループの育て方
- 障害対応と運用知見（**今日の経験を全部反映**）
- トラブルシューティング
- **Claude Code への指示プロンプトテンプレート**

これがあれば、購入者は「@BLUEPRINT.md を読んでセットアップして」と Claude Code に投げるだけで対話的にセットアップが進む状態になります。

## 9. 残った時間で大型機能を 3 つ実装

夕方、オーナーから「次の改善案は？」と聞かれて、ベスト 3 を提示しました。

1. **メトリクス → feedback 自動転記**
2. **Threads トークン自動更新**
3. **画像投稿対応**

そして「おすすめでお願い」で、全部実装しました。

### 9-1. メトリクス → feedback 自動転記

これが**今日の改修で最重要**です。

従来は「**オーナーが手動で `/feedback` を打つ → AI が読む**」のループでした。これだとオーナーの稼働が常に必要で、本物の半自動化ではない。

新しい `metrics_to_feedback.py` は、22:00 にメトリクス取得した後、**実績データから「伸びた投稿」「スベった投稿」を自動判定して feedback に追記**します。

判定ロジックは `mean ± 1σ` で、上振れと下振れを抽出。重複防止のため `media_id` で同一性チェック。データ不足（N<3）の時は安全スキップ。

これで AI 側だけで学習サイクルが回り始めます。**「AI が自分で育つ」**状態の第一歩。

### 9-2. Threads トークン自動更新

Threads の長期アクセストークンは**60日で切れます**。これを放置すると `THREADS_TOKEN_EXPIRES=2026-07-12` の翌日から全自動投稿が止まる。確実に発生する障害です。

`refresh_threads_token.py` は、毎週日曜 03:00 に走らせて、既存トークンを新しい60日トークンに交換。`.env` を上書きする前にタイムスタンプ付きバックアップを取って、失敗時の戻し手段も担保しました。

これで「60日後に止まる」が確定事故から「ありえない事故」に降格。

### 9-3. 画像投稿対応

ソーダ式・あわを式の検証で**「短文+スクショが最強」**が証明済み。テキストオンリーは伸びの天井がある。

`_threads_api.py` に `create_image_post(text, image_url)` を追加し、下書きの frontmatter に `image_url` フィールドを足しました。Discord Bot の `/queue` でも `image_url` を渡せるように。

Threads API は「パブリックにアクセスできる URL」が必要なので、現状は URL 前提の実装。Phase 2 で Discord 添付画像をそのまま使う案や、Cloudflare R2 アップロード対応を検討予定です。

## 10. Day 2 の終わりに

朝、投稿失敗から始まった一日が、**システム全体の進化で終わりました。**

| Before (Day 1 終了時) | After (Day 2 終了時) |
|----------------------|---------------------|
| テキスト投稿のみ | 画像投稿対応 |
| 60日後に確実に止まる | 自動更新で実質無期限 |
| feedback はオーナー手動 | 投稿実績から自動転記 |
| Bot コマンド 16 種 | Bot コマンド 17 種 (/post_bulk 追加) |
| 設計書なし | BLUEPRINT.md (配布物相当) |
| Modern Standby で死ぬ | DNS リトライ + OS 設定で堅牢化 |

正直、朝の時点では「今日 1 日リカバリで潰れるかも」と思っていました。実際には、リカバリしながら新機能を 3 つ追加し、配布商品の土台まで作れました。

**自動化開発の面白さって、こういう瞬間にあると思います。**

止まった原因を追跡することで、システムの弱いところが見える。直すついでに「ここも改善しよう」が連鎖する。気づいたら Day 1 より明らかに強くなってる。

## 11. 学びまとめ

今日の経験で再認識した 5 つの原則です。

1. **「電源繋いでる」は「スリープしない」を保証しない** — Modern Standby を知らないと Windows 11 で確実に踏む
2. **自動化スクリプトは「ネット復帰待ち」を必ず挟む** — `socket.gethostbyname` のリトライで充分
3. **ヘッドレス実行は生 stdout/stderr を必ずログに残す** — `exit=0 で 0 件生成` のような事故が後追いできる
4. **フィードバックループは AI 側で完結させる** — 「オーナーが打つ」から「AI が育つ」への進化が半自動化の本質
5. **物語性のある記録を残す** — Day 2 の経験そのものが note 連載のコンテンツになる

最後の 5 については、今あなたが読んでいるこの記事自体が証拠です。**作りながら note の記事も同時に進む**運用ができれば、開発時間と発信時間の両方が同時に消化される。これが noter として自動化を組む最大のメリットかもしれません。
